The Midnight Vault, taken for €0

A storefront refuses to apply the same coupon twice — but it only checks the last one. Alternate two valid codes and both keep stacking, uncapped, straight past a 100% discount. A €666 item checks out for nothing.

The shop

Target challenge-1026.challenges.intigriti.io Item The Midnight Collection · €666 Credit €66 Auth none

A single luxury product sits behind a cart and a coupon field. Two promotions exist. NIGHT20 (20% off) is printed in the announcement bar. NEWS30 (30% off) is handed back only after you subscribe to the newsletter — POST /api/newsletter returns the code, so it has to be unlocked once before it will resolve.

Checkout is gated by a server flag, canCheckout, which only flips to true when the order total reaches zero. So the whole challenge is one question: can an unauthenticated visitor drive the total to €0?

The flaw: a one-entry memory

Applying a coupon twice is supposed to be rejected. It is — but the duplicate check compares an incoming code only against the most recently applied promotion, not against everything already on the cart. The guard has a memory one entry deep.

That is harmless with one coupon. It breaks the moment a different code is applied in between: now the "last applied" promotion is the other one, so re-applying the first sails through. And the discounts add rather than compound, with no ceiling — so alternating two codes walks the discount up in steps of 20 and 30 until it passes 100%.

The exploit

Subscribe once to unlock NEWS30, add the vault to the cart, then apply the two codes in alternation. Four applications is all it takes:

# each request is the same endpoint — the order is the payload
POST /api/cart/coupon  {"code":"NIGHT20"}
POST /api/cart/coupon  {"code":"NEWS30"}
POST /api/cart/coupon  {"code":"NIGHT20"}  ← passes: NEWS30 was the last entry
POST /api/cart/coupon  {"code":"NEWS30"}  ← passes: NIGHT20 was the last entry

Total hits zero, canCheckout flips, and POST /api/checkout returns a confirmed receipt with the flag.

The wrong turn (and why the bug is really the dedupe)

A space-prefixed " NIGHT20" stacked on my first attempt, so I assumed a trim-versus-dedupe mismatch — the classic "normalize in one place, compare in another" bug. Rebuilding from a clean session killed that theory: I had simply used NEWS30 in between without noticing.

On a fresh session with only NIGHT20 applied, the parser is airtight — every disguised re-application is refused:

night20          "Coupon already applied."
NiGhT20          "Coupon already applied."
" NIGHT20"       "Coupon already applied."
"\u0009NIGHT20"  "Coupon already applied."
"\u000bNIGHT20"  "Coupon already applied."

Case-folding and whitespace-trimming both work correctly. The guard only fails once a different coupon sits between a code and its repeat — which is exactly what makes the last-entry-only comparison the vulnerability, not input parsing.

Impact

An unauthenticated visitor pays nothing for any item in the shop. The cumulative discount is uncapped, so the order total can be driven to zero regardless of price — here a €666 item taken for €0.00, and the order is accepted: /api/checkout returns a confirmed receipt with "paid": 0. No account, no privilege, no user interaction — four ordinary API calls in a specific order. On a real storefront this is direct, repeatable, trivially scriptable revenue loss.

The fix

Compare every incoming coupon against all promotions currently on the cart, not just the most recent one — the single-entry comparison is what lets two alternating codes re-apply forever.

Independently, clamp the cumulative discount at 100% of the subtotal and reject any checkout whose total falls below the intended floor. Then a stacking defect can't by itself produce a zero-cost order, and the same bug class can't resurface through a different code path.
